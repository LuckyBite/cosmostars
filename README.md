# Cosmostars · Автономное управление спутниковой группировкой

Веб-сервис оператора наземной смены: распределяет задания между аппаратами с учётом
энергии, температуры, калибровки и дефицита наземной связи, продолжает смену после
новых сообщений и показывает, что именно было потеряно и почему.

КосмоХакатон 2026, кейс «Автономное управление спутниковой группировкой».

---

## Быстрый старт

Весь сервис — один контейнер: интерфейс собирается внутри и раздаётся тем же
процессом, поэтому ссылка одна, а CORS в работе не участвует.

```bash
docker build -t cosmostars . && docker run --rm -p 7860:7860 cosmostars
```

Пульт откроется на `http://127.0.0.1:7860`, документация API — на `/docs`.

Без Docker:

```bash
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt -r requirements-dev.txt
npm --prefix frontend ci && npm --prefix frontend run build
uvicorn backend.app.main:app
```

Сервис поднимется на `http://127.0.0.1:8000` и сам раздаст собранный пульт.
Пока `frontend/dist` не собран, работают только API и `/docs` — сервис скажет
об этом на корневой странице.

Разработка интерфейса с горячей перезагрузкой идёт отдельным сервером на 5173,
запросы к `/api` он проксирует на 8000:

```bash
npm --prefix frontend run dev
```

Запускать **из корня репозитория**: выданная библиотека `model/` и папка `data/`
разрешаются относительно него, тем же способом, что и в команде воспроизведения.

Без браузера, сразу числами:

```bash
python -m backend.cli sweep --scenarios P01_intro P02_shift P03_energy P04_demand
```

## Пульт

Смена считается целиком и мгновенно — сутки P04 с 8120 заданиями считаются за
0,7 секунды, — а проигрывается по записанной истории со скоростью до ×32.
Постановка прямо требует, чтобы пять минут модельного времени не стоили
оператору пяти минут ожидания.

| Экран | Что отвечает |
|---|---|
| **Смена** | итог на шаге курсора, потолок выполнимости, полоса связи с ценой слота, приём сообщений |
| **Полотно** | сетка 48 × 288: слева от курсора факт, справа — намерение планировщика при знании этого шага |
| **Аппараты** | заряд, температура, срок калибровки, журнал команд с причинами отказов |
| **Задания** | фильтры и разбор «почему не вышло» в три слоя |
| **Ветви** | дерево смены по шагу ветвления и сравнение пары с проверкой сопоставимости |
| **Проверка** | пересчёт выгрузки выданной библиотекой прямо в браузере |
| **Жюри** | маршруты по критериям оценки: кнопка приводит сервис в нужное состояние |

Две вещи, которые стоит открыть первыми.

**Туман войны.** На полотне два слоя поверх одной сетки. Левая половина — журнал
модели, она не перерисовывается никогда. Правая — расписание связи, построенное
на знании текущего шага, бледным. Сообщение, пришедшее на шаге 72, меняет только
правую половину: это и есть «применение новых сведений с момента их получения
без изменения выполненной истории», показанное, а не заявленное.

**Разбор задания.** Клик по заданию разводит три ответа, которые смешивать нельзя:
невозможно по данным (сертификат против сценария), проиграло контакт (кто занял и
что стоило бы его вернуть — считается повторным решением), не пустил аппарат
(причина из журнала модели). На P02 все 44 просроченных задания связи
попадают в первый слой: ни одно не потеряно алгоритмом.

Плитки итога показывают официальные показатели **на шаге курсора**. Сервис отдаёт
пошаговые приращения, приписанные ровно так, как их приписывает `summary()`
выданной библиотеки, поэтому сумма до курсора совпадает со сводкой независимого
прогона до того же шага — это проверяется тестом.

## Метод

Два ресурса в этом кейсе ведут себя по-разному, и планировщик обращается с ними по-разному.

### Наземная связь планируется точно, заранее

Контакт с Землёй доступен на 3% аппарато-шагов: в суточном сценарии 458 слотов при
потребности в 410 рабочих шагов, при глобальном лимите в две передачи на шаг. У 210
из 344 заданий слотов ровно столько, сколько нужно работы, — пропущенный слот уже
ничем не компенсируется.

Каждое downlink-задание закреплено за одним аппаратом, поэтому назначение сводится к
задаче о потоке: задание берёт `remaining_steps` различных слотов из своего окна
контактов, аппарато-шаг несёт одно задание, шаг — не более `downlink_parallel_limit`.
Задания предлагаются в порядке выбранной цели и принимаются, только если весь набор
остаётся выполнимым (`backend/app/planner/downlink.py`). Для односложных заданий такой
порядок оптимален; для многосложных даёт нижнюю оценку, и расстояние до потолка потока
сервис показывает отдельно.

Расписание перестраивается только когда реальность от него отклонилась: после
сообщения, после смены цели или когда обещанная передача была отклонена по энергии.

### Ретрансляция решается пошагово

Relay доступен почти всегда (99% аппарато-шагов), поэтому его ограничивают время
аппарата, заряд и срок калибровки — то, что известно только на самом шаге. Задания
ранжируются по срочности и цели, исполнитель выбирается из свободных допустимых по
остатку заряда. Калибровка ставится **до** того, как аппарат понадобится обещанной
передаче, а не после отказа.

### Невыполнимость доказывается, а не предполагается

Постановка требует проверяемого основания для утверждения о невозможности. Модуль
`backend/app/planner/feasibility.py` выдаёт два сертификата, не зависящих от планировщика:

- **по заданию** — пересечение окна выполнения с расписанием контактов его аппарата
  содержит меньше шагов, чем требуется работы;
- **по группе (Холл)** — downlink-задания одного аппарата, чьи окна лежат внутри
  интервала, конкурируют только за контакты внутри него; если их суммарная работа
  превышает число контактов, часть заданий сорвётся при любом плане.

События способны только убрать контакт (`close_downlink`) или доступность, но не
добавить, поэтому сертификат, выданный в начале смены, действует до её конца.

Сертификаты показываются **рядом** с официальными показателями, а не вместо них:
исключать невыполненные задания из знаменателя описание данных прямо запрещает.

### Расчёт детерминирован

Ни один модуль не обращается к генератору случайных чисел
(`grep -rn "random\|seed\|shuffle" backend/ model/` — пусто), поэтому повторный
прогон той же смены с той же целью даёт побитово те же команды, ту же сводку и
тот же журнал. Проверяется сравнением хешей двух независимых прогонов; настройки
планировщика (`calibration_lead = 6`, `relay_soc_floor_pct = 0`) лежат в выгрузке
внутри `run_metadata`.

**Цели расходятся только при перегрузке.** На P02 и P03 обе цели дают одно расписание —
всё выполнимое и так выполняется, выбирать не из чего. На P04 выбор появляется:
приоритетный режим берёт на 430 заданий приоритета 3 больше, коммерческий — на
6 196 $ больше выручки. Это и есть цена решения, которую видит оператор.

## Воспроизведение расчёта

Любая выгрузка проверяется выданной библиотекой без участия нашего кода:

```bash
python -m backend.cli run --scenario P02_shift --goal priority \
    --events examples/events_demo.json --out exports/p02-events.json
python model/operations.py --result exports/p02-events.json --output exports/replay.json
```

В репозитории лежат готовые выгрузки — `examples/runs/`: короткая смена P01 без
сообщений и она же с сообщениями под обе цели управления. Каждая проверяется той
же командой, а также кнопкой «проверить файл выгрузки» на вкладке «Проверка».
Суточная выгрузка весит около 10 МБ и поэтому не коммитится — она получается
командой выше.

Сводка воспроизведения совпадает со сводкой в выгрузке. Выгрузка содержит исходный
сценарий, полученные сообщения в порядке получения, команды, число выполненных шагов,
сводные показатели и `run_metadata` с целью, названием и версией алгоритма,
переключениями цели и происхождением ветви.

## Развёртывание

Сервис разворачивается **одним экземпляром**: смена живёт в памяти процесса, и это
осознанное ограничение — смена здесь живой объект, а не строка в базе. Балансировщик
с несколькими репликами развёл бы запросы одной смены по разным процессам, поэтому
автомасштабирование не используется. Перезапуск теряет открытые смены; жюри просто
открывает новую, каталог на месте.

```bash
docker build -t cosmostars .
docker run --rm -p 7860:7860 cosmostars
```

Образ собирает интерфейс внутри себя (`node:22-alpine` → `npm run build`), кладёт
`frontend/dist` рядом с сервисом и запускает `uvicorn` на `${PORT:-7860}`.
Секретов, ключей и внешних сервисов нет: контейнеру нужен только порт.

Публикация на Hugging Face Spaces (бесплатно, один контейнер, постоянный HTTPS-адрес):

```bash
deploy/push-space.sh <owner>/<space-name>
```

Space создаётся один раз вручную с SDK **Docker**; скрипт копирует туда сервис,
подставляет свой `README.md` с front matter Space (`deploy/space-README.md`, иначе
настройки Space затёрлись бы нашим README) и пушит. Сборка идёт 3–5 минут.

Переменные окружения, все со значениями по умолчанию:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `7860` | порт сервиса |
| `COSMOSTARS_FRONTEND_DIR` | `frontend/dist` | откуда раздавать собранный пульт |
| `COSMOSTARS_ALLOWED_ORIGINS` | `*` | нужно только при раздельном хостинге фронта и API |
| `COSMOSTARS_MAX_RUNS` | `64` | сколько смен держать в памяти |
| `COSMOSTARS_EXPORT_DIR` | `exports` | куда пишет выгрузки CLI |

## Структура

```
model/            выданная расчётная библиотека, используется как есть
data/             сценарии кейса          examples/  сообщения и сохранённые расчёты
backend/app/
  planner/        flow.py      максимальный поток (Диниц)
                  downlink.py  точное расписание наземной связи
                  smart.py     планировщик команды
                  baseline_edf.py  простое правило для сравнения
                  feasibility.py   сертификаты невыполнимости
                  view.py      read-only доступ к состоянию среды
  core/           run.py, registry.py, compare.py, scenarios.py
  api/            routes.py, schemas.py
backend/cli.py    пакетные эксперименты и выгрузки
frontend/src/
  api/            клиент сервиса и типы ответов
  components/     экраны пульта; CanvasPanel — полотно с туманом войны
  styles/base.css дизайн-система, перенесённая из docs/proto/console.html
  derive.ts       всё, что считается из компактной сетки смены
tests/            31 тест: учёт, лимиты, события, ветви, сертификаты, API,
                  сходимость плиток пульта со сводкой библиотеки
docs/             постановка, описание данных, критерии, рабочий план
deploy/           публикация на Hugging Face Spaces
CASE_AUDIT.md     критерий → артефакт → честный статус
```

### Почему библиотека не переписана

`model/resource_env.py` и `model/operations.py` подключены напрямую. Переписывание
физики на другом стеке дало бы второй источник истины и расхождение в учёте, а
`Session.fork()` и `replay_episode()` уже закрывают ветвление и воспроизведение.
Планировщик читает состояние через тонкий адаптер `planner/view.py`, минуя
`observation()`: та копирует все задания на каждом вызове, что на сценарии с 8120
заданиями стоит около 18 секунд за смену.

## Тесты

```bash
python -m pytest tests -q
```

Проверяются учёт и лимиты (ни одна команда не отклонена, не более двух передач на шаг,
одно задание — один исполнитель), продолжение после событий (заряд, температура,
калибровка и прогресс сохраняются; повторное и некорректное сообщение отклоняется без
повреждения состояния), независимость ветвей, совпадение выгрузки с воспроизведением и
то, что задания с сертификатом невыполнимости действительно не выполняются за смену.

Отдельный файл `tests/test_console_api.py` держит обещания, которые пульт даёт на
экране: приращения показателей суммируются в сводку библиотеки шаг в шаг, клетки
полотна совпадают с журналом модели, `POST /verify` признаёт испорченную выгрузку
разошедшейся, а не «почти сошедшейся», у каждой ненулевой цены слота названо
основание, и все 44 просроченных задания связи на P02 отдают сертификат.

---

## Границы решения

- Порядок отбора downlink-заданий оптимален для односложных заданий; для многосложных
  это нижняя оценка, расстояние до потолка потока сервис показывает честно.
- Relay решается жадно и оптимальности не гарантирует; на P02 и P03 это не связывает,
  на P04 связывает, и разрыв виден в таблице.
- Энергетический горизонт учитывается через выбор исполнителя по заряду, а не через
  явное планирование заряда на ночь.
- Смены живут в памяти процесса: сервис разворачивается одним экземпляром, а
  перезапуск теряет открытые смены.
- Пульт рассчитан на экран от 1100 px; мобильной вёрстки нет.
- Намерение справа от курсора рисуется только по наземной связи. Ретрансляция
  решается пошагово и заранее не обещается — показывать там нечего, кроме окон.

Самопроверка по критериям с честными статусами — в [CASE_AUDIT.md](CASE_AUDIT.md).
