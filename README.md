# Cosmostars · Автономное управление спутниковой группировкой

Веб-сервис оператора наземной смены: распределяет задания между аппаратами с учётом
энергии, температуры, калибровки и дефицита наземной связи, продолжает смену после
новых сообщений и показывает, что именно было потеряно и почему.

КосмоХакатон 2026, кейс «Автономное управление спутниковой группировкой».

**Развёрнутый сервис: https://161-104-54-14.sslip.io**

Открывается без установки и без регистрации. Быстрый путь для эксперта — вкладка
**«Жюри»**: восемь маршрутов по критериям, каждый в один клик приводит сервис в
состояние, где соответствующий критерий можно проверить своими руками.
Документация API — на [`/docs`](https://161-104-54-14.sslip.io/docs).

## Быстрый старт

Весь сервис — один контейнер: интерфейс собирается внутри и раздаётся тем же
процессом, поэтому ссылка одна, а CORS в работе не участвует.

```bash
docker build -t cosmostars . && docker run --rm -p 7860:7860 cosmostars
```

Пульт откроется на `http://127.0.0.1:7860`, документация API — на `/docs`.

Без Docker (Python 3.11 или новее, Node 22 для сборки интерфейса):

```bash
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt -r requirements-dev.txt
npm --prefix frontend ci && npm --prefix frontend run build
uvicorn backend.app.main:app
```

Сервис поднимется на `http://127.0.0.1:8000` и сам раздаст собранный пульт.
Пока `frontend/dist` не собран, работают только API и `/docs` — сервис скажет
об этом на корневой странице.

Разработка интерфейса с горячей перезагрузкой идёт отдельным сервером на 5173,
запросы к `/api` он проксирует на 8000:

```bash
npm --prefix frontend run dev
```

Запускать **из корня репозитория**: выданная библиотека `model/` и папка `data/`
разрешаются относительно него, тем же способом, что и в команде воспроизведения.

Без браузера, сразу числами:

```bash
python -m backend.cli sweep --scenarios P01_intro P02_shift P03_energy P04_demand
```

Все числа из этой записки получаются одной командой — `sh experiments.sh`;
любой блок можно взять отдельно (`sweep`, `ceiling`, `feasibility`, `tune`,
`replay`).

## Пульт

Смена считается целиком и мгновенно — сутки P04 с 8120 заданиями считаются за
0,7 секунды, — а проигрывается по записанной истории со скоростью до ×32.
Постановка прямо требует, чтобы пять минут модельного времени не стоили
оператору пяти минут ожидания.

| Экран | Что отвечает |
|---|---|
| **Смена** | итог на шаге курсора, потолок выполнимости, полоса связи с ценой слота, приём сообщений |
| **Полотно** | сетка 48 × 288: слева от курсора факт, справа — намерение планировщика при знании этого шага |
| **Аппараты** | заряд, температура, срок калибровки, журнал команд с причинами отказов |
| **Задания** | фильтры и разбор «почему не вышло» в три слоя |
| **Ветви** | дерево смены по шагу ветвления и сравнение пары с проверкой сопоставимости |
| **Проверка** | пересчёт выгрузки выданной библиотекой прямо в браузере |
| **Жюри** | маршруты по критериям оценки: кнопка приводит сервис в нужное состояние |

На стартовом экране условия смены меняются до запуска, как требует постановка:
начальный заряд выбранного аппарата, коэффициент солнечной мощности, приоритет
существующего задания и период недоступности. Изменённый вариант сохраняется
отдельным сценарием со своим идентификатором и записью происхождения в `meta`,
поэтому сравнение с исходной сменой предупредит, что условия разные, а выгрузка
производной смены несёт в себе, что именно было изменено.

Две вещи, которые стоит открыть первыми.

**Туман войны.** На полотне два слоя поверх одной сетки. Левая половина — журнал
модели, она не перерисовывается никогда. Правая — расписание связи, построенное
на знании текущего шага, бледным. Сообщение, пришедшее на шаге 72, меняет только
правую половину: это и есть «применение новых сведений с момента их получения
без изменения выполненной истории», показанное, а не заявленное.

**Разбор задания.** Клик по заданию разводит три ответа, которые смешивать нельзя:
невозможно по данным (сертификат против сценария), проиграло конкуренцию, не пустил
аппарат (причина из журнала модели). Второй слой для связи называет, кто занял
контакт — впереди курсора по расписанию, позади него по журналу, так что ответ не
исчезает вместе со сроком, — и пока окно открыто, считает цену размена повторным
решением. Для ретрансляции он показывает, чем были заняты допустимые аппараты и
почему простаивали: не успеть к сроку, заряд ниже резерва, калибровка истекла,
аппарат недоступен. Групповой сертификат Холла идёт отдельным вердиктом: он
доказывает нехватку контактов группе заданий, а не невозможность конкретного
задания — какое из них выпадет, выбирает планировщик, и второй слой это
показывает. На P02 все 44 просроченных задания связи попадают в первый слой:
ни одно не потеряно алгоритмом.

Плитки итога показывают официальные показатели **на шаге курсора**. Сервис отдаёт
пошаговые приращения, приписанные ровно так, как их приписывает `summary()`
выданной библиотеки, поэтому сумма до курсора совпадает со сводкой независимого
прогона до того же шага — это проверяется тестом.

## Метод

Два ресурса в этом кейсе ведут себя по-разному, и планировщик обращается с ними по-разному.

### Наземная связь планируется точно, заранее

Контакт с Землёй доступен на 3% аппарато-шагов: в суточном сценарии 458 слотов при
потребности в 410 рабочих шагов, при глобальном лимите в две передачи на шаг. У 210
из 344 заданий слотов ровно столько, сколько нужно работы, — пропущенный слот уже
ничем не компенсируется.

Каждое downlink-задание закреплено за одним аппаратом, поэтому назначение сводится к
задаче о потоке: задание берёт `remaining_steps` различных слотов из своего окна
контактов, аппарато-шаг несёт одно задание, шаг — не более `downlink_parallel_limit`.
Задания предлагаются в порядке выбранной цели и принимаются, только если весь набор
остаётся выполнимым (`backend/app/planner/downlink.py`). Для односложных заданий такой
порядок оптимален; для многосложных даёт нижнюю оценку, и расстояние до потолка потока
сервис показывает отдельно.

Расписание перестраивается только когда реальность от него отклонилась: после
сообщения, после смены цели или когда обещанная передача была отклонена по энергии.

### Ретрансляция решается пошагово

Relay доступен почти всегда (99% аппарато-шагов), поэтому его ограничивают время
аппарата, заряд и срок калибровки — то, что известно только на самом шаге. Задания
ранжируются по срочности и цели, исполнитель выбирается из свободных допустимых по
остатку заряда. Калибровка ставится **до** того, как аппарат понадобится обещанной
передаче, а не после отказа.

### Невыполнимость доказывается, а не предполагается

Постановка требует проверяемого основания для утверждения о невозможности. Модуль
`backend/app/planner/feasibility.py` выдаёт два сертификата, не зависящих от планировщика:

- **по заданию** — пересечение окна выполнения с расписанием контактов его аппарата
  содержит меньше шагов, чем требуется работы;
- **по группе (Холл)** — downlink-задания одного аппарата, чьи окна лежат внутри
  интервала, конкурируют только за контакты внутри него; если их суммарная работа
  превышает число контактов, часть заданий сорвётся при любом плане.

События способны только убрать контакт (`close_downlink`) или доступность, но не
добавить, поэтому сертификат, выданный в начале смены, действует до её конца.

Сертификаты показываются **рядом** с официальными показателями, а не вместо них:
исключать невыполненные задания из знаменателя описание данных прямо запрещает.

### Расчёт детерминирован

Ни один модуль не обращается к генератору случайных чисел
(`grep -rn "random\|seed\|shuffle" backend/ model/` — пусто), поэтому повторный
прогон той же смены с той же целью даёт побитово те же команды, ту же сводку и
тот же журнал. Проверяется сравнением хешей двух независимых прогонов; настройки
планировщика (`calibration_lead = 6`, `relay_soc_floor_pct = 0`) лежат в выгрузке
внутри `run_metadata`.

### Расписание связи достигает оптимума потока

Порядок отбора downlink-заданий доказуемо оптимален для односложных заданий, а
для многосложных даёт лишь нижнюю оценку. Вместо того чтобы на этом остановиться,
разрыв измерен: сверху берётся расслабленный оптимум потока, который игнорирует
правило «оплачивается только завершённое задание» и поэтому недостижим ни для
какого планировщика.

```bash
python -m backend.cli ceiling
```

На всех четырёх сценариях кейса порядок отбора не приближается к оптимуму, а

одно и то же число. Теоретическая оговорка про нижнюю оценку остаётся в силе,
но на этих данных она не стоит ни одного шага работы.

### Ретрансляция: потолок и то, что упущено

Связь решается точно, ретрансляция — пошагово, поэтому утверждение о её качестве
нуждается в мерке со стороны. Мерок две, и они отвечают на разные вопросы.

```bash
python -m backend.cli bound
```

**Потолок потока** — максимум работы, который позволяют контакты и время
аппаратов: задание берёт свои шаги только там, где его тип связи открыт и
аппарат допущен, один аппарат делает одно дело за шаг. Потолок отбрасывает
энергию, температуру, калибровку, лимит двух передач на шаг и правило «оплачивается
только завершённое». Снятие ограничений может только поднять оптимум, поэтому
превзойти это число не может никакой планировщик — но именно поэтому оно щедрое.

**Упущенные аппарато-шаги** — наоборот, только то, что было доступно по-настоящему:
аппарат простаивал, связь была открыта, заряд выше резерва, калибровка в силе, и
для него было незанятое задание с несделанной работой.

| Сценарий | Потолок ретрансляции | Полезной работы | % потолка | Упущено аппарато-шагов |
|---|---:|---:|---:|---:|
| P02_shift | 1707 | 1707 | **100%** | **0** |
| P03_energy | 1707 | 1707 | **100%** | **0** |
| P04_demand | 13 723 | 10 991 | 80% | **813** из 13 723 |

На суточных сценариях жадное правило не «близко к оптимуму», а достигает его:
1707 из 1707, и ни одного аппарато-шага, который можно было занять и не заняли.
Вместе со связью получается 2029 полезных шагов из 2073 — недостающие 44 это ровно
та работа, которая лежит в заданиях с сертификатом невыполнимости.

На перегруженном P04 разрыв есть, и он измерен с двух сторон. Расслабленный потолок
показывает 20%, но настоящая упущенная возможность — 813 аппарато-шагов, то есть 6%
потолка. Остальное — не алгоритм, а физика, которую потолок отказывается замечать:
из простоев с открытой связью и доступной работой 470 пришлись на заряд ниже
резерва и 31 на истёкшую калибровку. Плюс 716 шагов ушли в задания, которые так и
не завершились, — это цена пошагового решения без обязательств на будущее.

Отсюда честная граница применимости: **ретрансляция связывает результат только при
перегрузке, и цена этого — около 6% возможной работы по ретрансляции на P04.**
На остальных сценариях кейса она не теряет ничего.

### Точное паросочетание для ретрансляции: попробовали, проигрывает

Диагностика выше показала, где именно жадное правило теряет работу на P04: 812
аппарато-шагов, где задание было, оно ещё успевало к сроку, связь была открыта,
заряда хватало. Причина структурная — жадное назначение это жадное паросочетание.
Задание берёт самый заряженный свободный аппарат из своего списка, и следующее,
которому подходил только этот аппарат, остаётся без исполнителя. На шаге 224
сценария P04 в очереди 230 заданий со списками допустимых аппаратов по два-четыре:
ровно та обстановка, где жадность ошибается.

Поэтому в сервисе есть третий планировщик — `cosmostars-match`. Он отличается от
нашего ровно одним: ретрансляция раздаётся поиском дополняющих путей (алгоритм
Куна) вместо жадного выбора. Наземная связь, упреждающая калибровка и порядок
предпочтения унаследованы без изменений, чтобы сравнение говорило только о раздаче.

P04_demand, перегрузка:

| Планировщик | Цель | Завершено | П3 в срок | Выручка, $ | Работа впустую |
|---|---|---:|---:|---:|---:|
| **cosmostars** | приоритет | **5801** | **1641** | 165 225 | 716 |
| cosmostars-match | приоритет | 5702 | 1634 | **170 451** | **641** |
| **cosmostars** | выручка | **5728** | **1211** | 171 421 | 670 |
| cosmostars-match | выручка | 5654 | 1208 | **174 912** | **590** |

На P02 и P03 разницы нет вовсе или она отрицательная: жадное правило там уже
достигает потолка, а точное паросочетание на P03 даёт 1144 задания против 1164.

Вывод, который стоит прочитать целиком: **пошаговая оптимальность не
складывается в оптимальность смены.** Паросочетание обслуживает на шаге не меньше
пар, чем жадность, — но только при одном и том же состоянии. Энергия связывает
шаги, состояния расходятся после первого же различия, и дальше сравнивать
по-шагово нечего. Плюс оплачивается только завершённое задание: паросочетание
размазывает работу по большему числу заданий, поэтому у него меньше работы
впустую и больше выручки — оно заканчивает более крупные и дорогие задания, — но
меньше завершений и меньше обязательств приоритета 3.

Под целью «приоритет», которую кейс ставит первой, наш планировщик лучше по обоим
главным показателям. Поэтому он и остался по умолчанию. Но `cosmostars-match`
доступен в интерфейсе и в CLI: утверждение проверяется, а не принимается на слово.

### Настройки планировщика выбраны по прогонам, а не наугад

У планировщика две настройки: `calibration_lead` — за сколько шагов до истечения
калибровки начинать её, если аппарат нужен обещанной передаче, и
`relay_soc_floor_pct` — ниже какого заряда не брать ретрансляцию.

```bash
python -m backend.cli tune --param calibration_lead --values 0 3 6 12 24
```

P03_energy, дефицит энергии:

| `calibration_lead` | Завершено | П3 в срок | Работа впустую | Шагов ниже резерва | Мин. заряд |
|---:|---:|---:|---:|---:|---:|
| 0 | 1157 | 311 | 2 | 6 | 27,9% |
| 3 | 1164 | 315 | 0 | 6 | 27,9% |
| **6** | **1164** | **315** | **0** | **6** | **27,9%** |
| 12 | 1164 | 315 | 0 | 17 | 24,9% |
| 24 | 1083 | 284 | 29 | 1260 | 19,3% |

P04_demand, перегрузка:

| `calibration_lead` | Завершено | П3 в срок | Шагов ниже резерва |
|---:|---:|---:|---:|
| 0 | 5814 | 1647 | 495 |
| 3 | 5808 | 1644 | 491 |
| **6** | **5801** | **1641** | **477** |
| 12 | 5719 | 1640 | 469 |
| 24 | 4693 | 1531 | 273 |

Читается это так. Слишком поздняя калибровка (0) на дефицитном сценарии стоит
семи заданий и четырёх обязательств: аппарат оказывается непригоден в момент
обещанной передачи. Слишком ранняя (24) разрушает смену на обоих сценариях —
калибровка тратит энергию и занимает время, которое нужно работе. Между 3 и 12
результат по заданиям на P03 не меняется вообще, а по энергии лучше 3–6.
На P04 виден честный размен: меньший упреждающий срок берёт на 13 заданий больше,
но проводит на 18 аппарато-шагов больше ниже резерва. Значение 6 стоит на плато
по P03 и рядом с лучшим по P04 — поэтому оно и выбрано.

`relay_soc_floor_pct` на P03 не меняет ничего до 40 и начинает стоить заданий
на 60 (1155 против 1164, 6 шагов работы впустую). Поэтому он и оставлен нулевым:
выбор исполнителя по остатку заряда уже делает эту работу, а явный порог только
отнимает исполнителей.

Проверено по всей решётке — две настройки, четыре сценария, обе цели:

- `relay_soc_floor_pct = 0` оказывается лучшим **во всех восьми комбинациях**;
- у `calibration_lead` значения, лучшего везде, не существует: на P02 и P03 лучшие
  результаты дают 3 и 6 (они совпадают), на P01 и P04 — 0. Значение 6 выбрано
  как компромисс, и цена компромисса названа выше: 13 заданий на P04 в обмен на
  18 аппарато-шагов запаса по энергии. Утверждать, что настройка «оптимальна»,
  мы не можем и не будем.

**Цели расходятся только при перегрузке.** На P02 и P03 обе цели дают одно расписание —
всё выполнимое и так выполняется, выбирать не из чего. На P04 выбор появляется:
приоритетный режим берёт на 430 заданий приоритета 3 больше, коммерческий — на
6 196 $ больше выручки. Это и есть цена решения, которую видит оператор.

## Учёт сверяется не сам с собой

Проверка воспроизводимости отвечает на вопрос «повторяется ли расчёт» — и
отвечает силами той же выданной библиотеки. У такой проверки есть предел:
библиотека сверяется сама с собой.

Поэтому есть вторая, независимая. `backend/app/core/audit.py` пересчитывает
исполненную историю по описанию модели, ни разу не обращаясь к `model/`:
мощность по исполненной команде, включение обогрева по температуре до шага,
энергию с КПД заряда и разряда и запретом заряда вне температурного окна,
экспоненциальную релаксацию температуры, прогресс по каждому заданию, шаг
завершения, выручку, обязательства и число отклонённых команд.

На суточной смене это 13 824 строки журнала, и расходится из них ноль — ни по
физике, ни по учёту, включая шаг завершения каждого задания. Отчёт доступен
ручкой `GET /api/runs/{id}/audit` и вкладкой **«Проверка»**, так что эксперту
не нужно верить нам на слово: он видит, что две независимые реализации
согласны.

Отдельно проверено, что модель действительно отклоняет недопустимое, а не
принимает всё подряд: `tests/test_model_enforces_limits.py` намеренно подаёт
команды мимо нашего планировщика — задание вне окна, задание недопустимому
аппарату, передачу без контакта, одно задание двум аппаратам на одном шаге и
третью одновременную передачу — и сверяет причину каждого отказа. Это то, что
делает `blocked_command_count = 0` в таблице результатов содержательным: ноль
там стоит потому, что планировщик проверяет допустимость до отправки, а не
потому, что проверять некому.

## Воспроизведение расчёта

Любая выгрузка проверяется выданной библиотекой без участия нашего кода:

```bash
python -m backend.cli run --scenario P02_shift --goal priority \
    --events examples/events_demo.json --out exports/p02-events.json
python model/operations.py --result exports/p02-events.json --output exports/replay.json
```

В репозитории лежат готовые выгрузки — `examples/runs/`: короткая смена P01 без
сообщений и она же с сообщениями под обе цели управления. Каждая проверяется той
же командой, а также кнопкой «проверить файл выгрузки» на вкладке «Проверка».
Суточная выгрузка весит около 10 МБ и поэтому не коммитится — она получается
командой выше.

Сводка воспроизведения совпадает со сводкой в выгрузке. Выгрузка содержит исходный
сценарий, полученные сообщения в порядке получения, команды, число выполненных шагов,
сводные показатели и `run_metadata` с целью, названием и версией алгоритма,
переключениями цели и происхождением ветви.

выполняются строго по очереди — у каждой смены свой замок, — поэтому вторая
вкладка или маршрут жюри, запущенный во время ручного шага, ждут, а не портят
состояние; это закреплено тестом на параллельное продвижение.

## Развёртывание

Сервис разворачивается **одним экземпляром**: смена живёт в памяти процесса, и это
осознанное ограничение — смена здесь живой объект, а не строка в базе. Балансировщик
с несколькими репликами развёл бы запросы одной смены по разным процессам, поэтому
автомасштабирование не используется. Единственный долговечный артефакт — выгрузка,
которую оператор скачивает сам, так что эфемерная файловая система сервису безразлична.

Локально:

```bash
docker build -t cosmostars .
docker run --rm -p 7860:7860 cosmostars
```

Образ собирает интерфейс внутри себя (`node:22-alpine` → `npm run build`), кладёт
`frontend/dist` рядом с сервисом и запускает `uvicorn` на `${PORT:-7860}`. Секретов,
ключей и внешних сервисов нет: контейнеру нужен только порт.

### На VPS

Два файла делают всю работу: [`docker-compose.yml`](docker-compose.yml) поднимает
сервис и обратный прокси, [`Caddyfile`](Caddyfile) выдаёт TLS.

```bash
git clone https://github.com/LuckyBite/cosmostars.git && cd cosmostars
cp .env.example .env          # вписать SITE_ADDRESS, если есть домен
docker compose up -d --build
```

Требования скромные: 1 ГБ памяти и 1 vCPU достаточно, 2 ГБ дают запас на
маршруты жюри со всеми ветвлениями. Диска хватит 10 ГБ.

Сборка интерфейса внутри образа хочет около гигабайта памяти, и на машине с
гигабайтом ей нужен своп. Собирать на сервере вообще не обязательно: CI
публикует тот же образ, который сам же поднял и проверил, поэтому достаточно
дописать в `.env` строку

```
COSMOSTARS_IMAGE=ghcr.io/luckybite/cosmostars:main
```

и поднять сервис командой `docker compose pull && docker compose up -d`.
Это те же секунды вместо минут сборки.

С доменом в `SITE_ADDRESS` Caddy сам получает сертификат Let's Encrypt и
продлевает его. Без домена сервис отвечает по HTTP на 80 порту — для кейса этого
достаточно: ни авторизации, ни секретов в сервисе нет. Если HTTPS всё-таки нужен,
а домена нет, подойдёт адрес вида `203-0-113-10.sslip.io`: он разрешается в тот же
IP, и сертификат на него выдаётся как на обычный домен.

Обновление после правки — `docker compose up -d --build`; смены при этом теряются,
потому что живут в памяти процесса.

### Бесплатный хостинг, если VPS нет

В репозитории лежит чертёж [`render.yaml`](render.yaml) — в панели Render это
**New → Blueprint** на этом репозитории, дальше без ручной настройки полей.
Бесплатный инстанс даёт 512 МБ и 750 инстанс-часов в месяц: этого хватает ровно на
один круглосуточный сервис, что нам и нужно.

Одна особенность, о которой лучше знать заранее: бесплатный инстанс **засыпает
после 15 минут без входящего трафика** и просыпается около минуты. Эксперт, открывший
ссылку и не дождавшийся ответа, просто закроет её, поэтому в репозитории есть задача
[`keepwarm.yml`](.github/workflows/keepwarm.yml): она пингует `/api/health` каждые
десять минут, если задать переменную репозитория `SERVICE_URL`. Тот же эффект даёт
любой внешний пингер — это не требование к сервису, а свойство бесплатного тарифа.

Память под смены ограничена сознательно: полная смена стоит около 17 МБ на суточном
сценарии и 26 МБ на перегруженном. Тринадцатая смена вытесняет ту, которую дольше
всех не открывали, а не самую старую — смена, открытая у эксперта в браузере, обычно
как раз самая старая в процессе.

Переменные окружения, все со значениями по умолчанию:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `7860` | порт сервиса; на Render задаётся платформой |
| `SITE_ADDRESS` | — | домен для TLS в `docker-compose.yml`; пусто — HTTP на :80 |
| `COSMOSTARS_MAX_RUNS` | `12` | сколько смен держать в памяти (в compose — 32, на развёрнутом сервере с 1 ГБ — 16) |
| `COSMOSTARS_FRONTEND_DIR` | `frontend/dist` | откуда раздавать собранный пульт |
| `COSMOSTARS_ALLOWED_ORIGINS` | `*` | нужно только при раздельном хостинге фронта и API |
| `COSMOSTARS_EXPORT_DIR` | `exports` | куда пишет выгрузки CLI |

### Почему библиотека не переписана

`model/resource_env.py` и `model/operations.py` подключены напрямую. Переписывание
физики на другом стеке дало бы второй источник истины и расхождение в учёте, а
`Session.fork()` и `replay_episode()` уже закрывают ветвление и воспроизведение.
Планировщик читает состояние через тонкий адаптер `planner/view.py`, минуя
`observation()`: та копирует все задания на каждом вызове, что на сценарии с 8120
заданиями стоит около 18 секунд за смену.

## Тесты

```bash
python -m pytest tests -q
python -m ruff check .          # стиль и типичные ловушки
python -m mypy                  # типы, настройки в pyproject.toml
```

Все три команды гоняются в CI на каждом пуше вместе со сборкой интерфейса и
сборкой образа, внутри которого поднимается контейнер и проверяется, что сервис
отвечает.

Проверяются учёт и лимиты (ни одна команда не отклонена, не более двух передач на шаг,
одно задание — один исполнитель), продолжение после событий (заряд, температура,
калибровка и прогресс сохраняются; повторное и некорректное сообщение отклоняется без
повреждения состояния), независимость ветвей, совпадение выгрузки с воспроизведением и
то, что задания с сертификатом невыполнимости действительно не выполняются за смену.

Отдельный файл `tests/test_console_api.py` держит обещания, которые пульт даёт на
экране: приращения показателей суммируются в сводку библиотеки шаг в шаг, клетки
полотна совпадают с журналом модели, `POST /verify` признаёт испорченную выгрузку
разошедшейся, а не «почти сошедшейся», у каждой ненулевой цены слота названо
основание, и все 44 просроченных задания связи на P02 отдают сертификат.

## Границы решения

- Порядок отбора downlink-заданий оптимален для односложных заданий; для многосложных
  это нижняя оценка, расстояние до потолка потока сервис показывает честно.
- Relay решается жадно и оптимальности не гарантирует; на P02 и P03 это не связывает,
  на P04 связывает, и разрыв виден в таблице.
- Энергетический горизонт учитывается через выбор исполнителя по заряду, а не через
  явное планирование заряда на ночь.
- Смены живут в памяти процесса: сервис разворачивается одним экземпляром, а
  перезапуск теряет открытые смены.
- Пульт рассчитан на экран от 1100 px; мобильной вёрстки нет.
- Намерение справа от курсора рисуется только по наземной связи. Ретрансляция
