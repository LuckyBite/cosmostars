# Фичи пульта: что берём и за какие баллы

**Статус: приняты все семь, 21.09.** Дедлайн сдачи — 22.09.2026 17:30 мск.
Документ продолжает [plan.md](plan.md) и описывает только продуктовую надстройку над ядром.

Принцип отбора: каждая фича обязана закрывать конкретный критерий из
[03-kriterii-ocenki.pdf](case/03-kriterii-ocenki.pdf). Красота без критерия не берётся.
Технические критерии Т1–Т6 — шлагбаум (до защиты пускают топ-25 по их сумме),
поэтому при нехватке времени первыми делаются фичи с меткой «Т».

## 1. Туман войны на Ганте

**Что это.** Гант делится курсором «сейчас». Слева — факт: что реально исполнилось,
с причинами отказов из журнала модели. Справа — намерение планировщика при текущем
знании, нарисованное бледно. Пришло событие — правая часть перерисовывается,
левая не меняется ни на пиксель.

**Зачем.** Т3 (10 баллов) требует «применение новых сведений с момента их получения
без изменения выполненной истории» и «будущие сообщения не используются до передачи
сервису». Обычно это утверждают словами. Мы показываем: до шага 72 планировщик про
срочную заявку не знал, и это видно на экране. Заодно снимается первое подозрение
технического эксперта — подглядывание в будущее.

**Как.** Намерение по связи уже отдаёт `GET /runs/{id}/downlink-plan`
(`DownlinkSchedule` из точного паросочетания). Для ретрансляции намерение
достраивается тем же правилом, что и на исполнении. Фронт рисует два слоя
поверх одной сетки 48 × 288 и не пересчитывает левый слой никогда.

**Проверка на защите.** Отмотать на шаг 71, вбросить `add_jobs`, показать, что
изменился только правый слой.

## 2. «Почему не вышло» — разбор по слоям

**Что это.** Клик по проваленному заданию или по простою аппарата открывает панель,
которая разбирает причину послойно:

1. **Физически невозможно** — сертификат из `planner/feasibility.py`:
   либо окно короче объёма работы (`contact_window_shorter_than_work`),
   либо группа заданий одного аппарата перекрывает все контакты интервала
   (`satellite_contacts_oversubscribed`, условие Холла).
2. **Проиграло конкуренцию** — слот занят другим заданием: показываем какое,
   его приоритет и цену, то есть цену размена.
3. **Не пустил аппарат** — причина прямо из `reason` в строке журнала:
   `energy_reserve`, `thermal_limit`, `calibration_required`, `no_contact`,
   `ground_capacity`, `ineligible_satellite`, `outside_job_window`.

**Зачем.** О3 (8 баллов) дословно: «участники различают ограничения задачи и
недостатки своего алгоритма; утверждение о невозможности выполнения имеет
проверяемое основание». Слой 1 — это ограничение задачи с доказательством,
слой 2 — осознанный размен, слой 3 — состояние аппарата. Разница между ними и есть
предмет критерия.

**Как.** Новая ручка `GET /runs/{id}/jobs/{job_id}/explain`, которая собирает три слоя
из уже существующих источников. Слой 2 берётся из решения паросочетания: кто занял
контакт, на который претендовало задание.

⚠️ Сертификаты выдаются только против данных, а не против «наш планировщик не нашёл».
Событие может лишь отнять контакт (`close_downlink`), но не добавить, поэтому
сертификат, выданный в начале смены, остаётся верным до конца.

## 3. Потолок выполнимости

**Что это.** Рядом с честными метриками показываем верхнюю границу: сколько заданий
по связи вообще выполнимо, если снять ограничения по энергии и оставить только окна
контакта и лимит в две передачи на шаг. И свой результат — в процентах от неё.

**Зачем.** О1 (10 баллов) про результат управления и объяснение потерь. Формулировка
«выполнимо 812, взяли 780, вот где потеряли 32» сильнее, чем «выполнили 780».
Основание для дефицита есть в данных: по группировке 458 аппарато-шагов с контактом
при потребности 410, у отдельного аппарата бывает 9 окон из 288 шагов.

**Как.** `downlink.ceiling()` уже считает границу, `GET /runs/{id}/feasibility` её отдаёт.
Осталось положить рядом с метриками смены и подписать, что это именно граница.

⚠️ Невыполнимые задания **не вычёркиваются** из знаменателя официальных метрик.
Потолок идёт отдельной строкой рядом. Иначе это читается как подгонка и бьёт по О3.

## 4. Дерево смены

**Что это.** Не две колонки сравнения, а граф истории: узел — точка, где оператор
остановился, от узла растут ветки. Можно вернуться в узел на шаге 72 и переиграть
иначе. Сравнение — выбрать два узла и получить дельту по приоритетным заданиям,
выручке и остатку ресурсов.

**Зачем.** О4 (7 баллов) требует, чтобы ветки стартовали из одного фактического
состояния при одинаковых условиях и событиях. В дереве это видно топологически,
а не декларируется в подписи.

**Как.** `Run.fork()` уже сохраняет `parent_id` и `forked_at_step`, `Session.fork()`
делает полную копию состояния. `GET /compare` уже проверяет сопоставимость ветвей
и выдаёт вердикт. Осталась отрисовка графа и выбор пары узлов.

**Что сравниваем на защите:** две цели управления из одной точки (приоритет против
выручки) и наш планировщик против baseline EDF.

## 5. Проверка расчёта в браузере

**Что это.** Вкладка: загрузить выгрузку → сервис сам прогоняет её через
`replay_episode` → показывает «сценарий совпал по хешу, 288 шагов пересчитаны,
метрики сошлись». Рядом — та же команда для запуска руками:

```
python model/operations.py --result result.json --output replay.json
```

**Зачем.** Т1 (10) и Т6 (4) оба упираются в воспроизводимость. Эксперт, увидевший
сходимость, не выходя из браузера, ставит балл сразу, а не после разворачивания репо.

**Как.** `POST /verify`: принимает `cosmo-B-ops-result-1.0`, вызывает
`replay_episode` с сохранённым сценарием, событиями, командами и `steps_executed`,
сверяет `digest` исходного сценария и метрики `summary()`, возвращает отчёт
о сходимости. Вся логика уже в выданной библиотеке.

## 6. Цена слота связи

**Что это.** Для каждого окна контакта показываем альтернативную стоимость: что мы
потеряли, отдав этот пятиминутный слот именно этому заданию. Полоса окон
раскрашивается по цене — видно, где группировка дерётся за связь, а где простаивает.

**Зачем.** О3 (обоснованность) и Т2 (12 баллов, там ценят объяснимость метода и
поведение при дефиците). Это переводит разговор из «алгоритм так решил» в
«слот стоил $40, и вот почему мы его отдали сюда».

**Как.** Число уже внутри решения паросочетания в `planner/downlink.py`:
берётся из сравнения оптимума с оптимумом при запрете этого назначения либо из
двойственных величин потока. Отдаём вместе с `downlink-plan`.

## 7. Вкладка «жюри»

**Что это.** Список критериев, у каждого кнопка «показать». Нажал О2 — сервис сам
загружает P02, докручивает до шага 72, вбрасывает демо-событие из
`examples/events_demo.json` и открывает нужный экран.

**Зачем.** О5 (7 баллов): «эксперт должен самостоятельно пройти основной сценарий».
О6: читаемость и регламент. Снимает риск, что лучшую часть продукта просто не найдут
за отведённые минуты.

**Как.** Пресет = сценарий + число шагов + событие + целевой экран. Хранится в конфиге
фронта, дёргает существующие ручки. Дублирует маршрутами содержание `CASE_AUDIT.md`.

## Не делаем

| Что | Почему |
|---|---|
| 3D-глобус, орбиты, зоны видимости | геометрии в данных нет вообще: у аппарата только батарея, температура и ватты, у окружения — `solar_w`, `thermal_target_c` и два булевых массива доступности. Орбиты пришлось бы выдумать, и они разошлись бы с окнами связи, по которым реально считается задача — прямой минус по Т1 и О3 |
| Реальное время (5 минут модели = 5 минут ожидания) | постановка прямым текстом: «Пять минут модельного времени не требуют пяти минут ожидания пользователя». Ожидание ломает О5: эксперт не пройдёт сценарий сам |
| RL, CP-SAT, авторизация, БД, мобильная вёрстка | не оплачивается ни одним критерием |

Проигрывание смены — это не реальное время: считаем мгновенно, проигрываем записанную
историю с управлением скоростью и остановкой на шаге. Ощущение живой смены есть,
ожидания нет, отмотать назад можно.

## Открытые вопросы

- Слой 2 в разборе причин («проиграло конкуренцию») и цена слота считаются из одного
  и того же места. Делать их одной задачей.
- Намерение по ретрансляции справа от курсора: пересчитывать на каждом шаге или
  показывать только связь. Решать по скорости отрисовки на P04 (8120 заданий).
- Дерево веток на демо должно быть маленьким: два-три узла, иначе не читается с экрана.
