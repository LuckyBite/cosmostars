## 2. Что строим

Оператор загружает сценарий → выбирает цель (приоритет / выручка) → считает до нужного шага → вбрасывает событие → продолжает → сравнивает две ветви → сохраняет выгрузку.

**Обязательный минимум:**

- загрузка сценария + валидация + карточка смены;
- пошаговый и ускоренный расчёт, остановка перед шагом;
- три типа событий (`add_jobs`, `satellite_outage`, `close_downlink`) — файлом и руками из UI;
- две цели управления, переключение на границе шага;
- ветвление из одного состояния + панель сравнения;
- экраны: расписание, аппараты (заряд/температура/калибровка), задания, журнал отклонённых команд;
- выгрузка `cosmo-B-ops-result-1.0`, воспроизводимая через `replay_episode`.

**Режем сразу:** 3D-глобус, авторизация, БД, RL, CP-SAT, мобильная вёрстка.

⚠️ `observation()` делает deepcopy всех заданий — на P04 это ~18 с за смену. Планировщик читает `session.env.state` / `session.env.jobs` напрямую. Сам шаг модели быстрый: 288 шагов за 0.08 с.

## 4. Ключевые решения по алгоритму

**Downlink — это вся задача.** Контакт с Землёй доступен 3% времени (458 аппарато-шагов при потребности 410), плюс глобальный лимит 2 передачи на шаг. 210 из 344 заданий идут впритык.

- **Downlink решаем точно** — двудольное паросочетание «задание → (аппарат, шаг)» с лимитом 2 на шаг. Размерность копеечная, считается мгновенно, даёт доказуемо лучший результат.
- **Relay — жадная эвристика** по плотности ценности с учётом остатка энергии и срока калибровки. В P02 не дефицитен, дефицит появляется в P04 (перегрузка) и P03 (энергия).
- **Baseline для сравнения** — жадный по ближайшему сроку (EDF). Реализуем сами, гоняем на тех же условиях.
- **Потолок выполнимости.** 44 из 344 downlink-заданий в P02 невыполнимы физически (в окне меньше слотов, чем работы) — $1366 и 19 заданий приоритета 3 недостижимы в принципе. В P01 таких 4 из 6. Это проверяемое основание для критерия О3.

⚠️ Выкидывать невыполнимые задания из знаменателя официальных метрик **запрещено**. Потолок показываем отдельной диагностикой рядом.
