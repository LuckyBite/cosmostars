# Критерий → артефакт → статус

Самопроверка команды против [критериев оценки](docs/case/03-kriterii-ocenki.pdf).
Для каждого критерия: чем он закрыт, где это смотреть и что именно **не** сделано.
Статусы поставлены по правилу «подтверждено расчётом или файлом, иначе не подтверждено».

Ссылка на развёрнутый сервис — в [README](README.md#развёртывание).
Быстрый путь для эксперта: вкладка **«Жюри»** — маршруты по критериям в один клик.

## Технические критерии

### Т1. Корректность модели и учёта — 0–10

| Чем закрыт | Где смотреть |
|---|---|
| Выданная библиотека `model/` подключена как есть, физика не переписана | [README · почему библиотека не переписана](README.md#почему-библиотека-не-переписана) |
| Планировщик не обходит проверки: все команды проходят `can_execute` до шага | `backend/app/planner/base.py`, `StepPlan` |
| Выгрузка пересчитывается `replay_episode` в браузере: хеш сценария, сводка, журнал построчно | вкладка **«Проверка»**, `POST /api/verify` |
| Ни одна команда не отклонена моделью на всех четырёх сценариях | `blocked_command_count = 0` в таблице результатов |
| 35 тестов на учёт, лимиты, события, ветви, сертификаты | `python -m pytest tests -q` |

**Статус: подтверждено.** Отдельно отметим: `blocked_command_count = 0` — это не
«модель ничего не проверяла», а следствие того, что планировщик сам проверяет
допустимость до отправки. Проверить можно, отключив проверку в `StepPlan.try_job`.

### Т2. Алгоритм планирования — 0–12

| Чем закрыт | Где смотреть |
|---|---|
| Наземная связь решается точно: двудольное паросочетание с лимитом на шаг | `backend/app/planner/downlink.py`, `flow.py` |
| Ретрансляция — пошаговое правило по срочности, цели и остатку заряда | `backend/app/planner/smart.py` |
| Калибровка ставится **до** того, как аппарат понадобится обещанной передаче | `_needs_calibration_soon` там же |
| Учитывается остаток работы, срок и цель управления | `job_score`, `StepView.slack` |
| Поведение при дефиците показано на P03 (энергия) и P04 (перегрузка) | таблица в README, маршруты жюри «Т2» |
| Цена слота связи: что стоило отдать этот контакт именно этому заданию | `downlink.slot_prices`, полоса связи на вкладке «Смена» |

**Статус: подтверждено.** Порядок отбора downlink-заданий оптимален для
односложных заданий, а для многосложных даёт нижнюю оценку — но разрыв измерен
и на всех четырёх сценариях равен нулю (`python -m backend.cli ceiling`):
отбор достигает оптимума потока, а не приближается к нему. Настройки выбраны по
прогонам, а не наугад (`python -m backend.cli tune`), и поведение вне выбранного
диапазона показано. Ретрансляция жадная и оптимальности не гарантирует, но её потеря измерена с двух
сторон (`python -m backend.cli bound`): на P02 и P03 она достигает потолка потока
(1707 из 1707) и не упускает ни одного аппарато-шага, на P04 упускает 813 из
13 723 — около 6%, причём из простоев с открытой связью 470 объясняются зарядом
ниже резерва, а не выбором задания.

### Т3. Продолжение расчёта и временная корректность — 0–10

| Чем закрыт | Где смотреть |
|---|---|
| Исполненная история не пересчитывается: курсор ходит по журналу, не по состоянию | вкладка **«Полотно»**, два слоя на одной сетке |
| Будущие сообщения не используются: намерение справа от курсора построено на знании этого шага | там же; `GET /runs/{id}/downlink-plan` с полем `built_at_step` |
| Заряд, температура, калибровка и прогресс сохраняются через событие | `tests/test_events_and_branches.py` |
| Событие не применяется повторно: библиотека отклоняет дубль идентификатора | тот же тест, `Session.apply_event` |
| Ветви независимы: `Session.fork()` копирует состояние целиком | тест независимости ветвей, дерево на вкладке «Ветви» |
| Некорректный ввод не повреждает состояние: причина возвращается, смена продолжается | форма «Своё сообщение» на вкладке «Смена» |

**Статус: подтверждено.** Проверка на защите: отмотать курсор на шаг 71, вбросить
`add_jobs`, показать, что изменился только правый слой полотна.

### Т4. Эксперименты и проверка результата — 0–8

| Чем закрыт | Где смотреть |
|---|---|
| Воспроизводимое сравнение с простым правилом на четырёх сценариях | `python -m backend.cli sweep`, таблица в README |
| Прогон после событий, те же условия для обоих планировщиков | `sweep --events examples/events_demo.json`, вторая таблица в README |
| Обычные и сложные условия разведены: P02 норма, P03 энергия, P04 перегрузка | те же таблицы |
| Настройки зафиксированы, случайности нет: ни один модуль не обращается к генератору | `grep -rn "random" backend/ model/` → пусто, два прогона дают побитово одно и то же |
| Чувствительность к настройкам показана по всей решётке: две настройки, четыре сценария, обе цели | `python -m backend.cli tune`, таблицы и вывод в README |
| Верхняя граница для ретрансляции измерена, а не заявлена | `python -m backend.cli bound`, `planner/bound.py` |
| Разрыв до теоретического оптимума измерен, а не описан словами | `python -m backend.cli ceiling` — нулевой на всех четырёх сценариях |
| Границы применимости названы | README · границы решения |

**Статус: подтверждено.** Ни одной оговорки не осталось: сравнение с простым
правилом воспроизводимо и на чистых сменах, и после одинаковых сообщений;
расчёт детерминирован и это проверено хешами; чувствительность к настройкам
пройдена по всей решётке; обе границы — по связи и по ретрансляции — измерены
и названы числами вместе с тем, что именно они игнорируют.

### Т5. Архитектура и качество кода — 0–6

| Чем закрыт | Где смотреть |
|---|---|
| Загрузка данных, планировщик, расчёт, события и интерфейс разделены | `backend/app/{core,planner,api}`, `frontend/src` |
| Точки входа очевидны: `uvicorn backend.app.main:app`, `python -m backend.cli`, `npm run dev` | README · быстрый старт |
| Конфигурация в одном месте, без путей с машины разработчика | `backend/app/core/config.py` |
| Ошибки — часть контракта: `ServiceError` → HTTP-код и текст для оператора | `backend/app/core/errors.py` |
| Секретов в репозитории нет; сервис не требует ни одного ключа | `.env` в `.gitignore`, переменных окружения с секретами нет |
| Ввод ограничен: тело запроса больше лимита отклоняется с внятной причиной | `limit_request_body` в `main.py`, 413 и текст для оператора |
| Стиль и типы проверяются машиной, а не на глаз | `ruff check .` и `mypy` — обе чисты, обе в CI, настройки в `pyproject.toml` |

**Статус: подтверждено.** Линтер и проверка типов проходят без замечаний и стоят
в CI перед тестами, так что «читаемо и без дублирования» — проверяемое утверждение,
а не самооценка. Остаётся одно свойство, и оно осознанное: смены живут в памяти
процесса (смена — живой объект, а не строка в БД), поэтому сервис разворачивается
одним экземпляром и перезапуск теряет открытые смены. Единственный долговечный
артефакт — выгрузка, и путь к ней у оператора и у команды воспроизведения один.

## Отраслевые критерии

### О1. Результат управления — 0–10

| Чем закрыт | Где смотреть |
|---|---|
| Результат по обязательствам, выручке и ресурсам на любом шаге смены | плитки итога на вкладке «Смена», курсор смены |
| Потери объяснены: потолок выполнимости рядом с честными метриками | карточка «Потолок выполнимости» |
| Вывод подтверждён расчётами на сопоставимых условиях | таблицы baseline vs cosmostars в README |
| Компромисс между целями измерен, а не назван | сравнение ветвей на P04: 362 обязательства против $5 338 |

**Статус: подтверждено.** Плитки показывают показатели на шаге курсора, сложенные
из тех же приращений, которыми их считает `summary()` библиотеки; совпадение с
независимым прогоном до того же шага проверено.

### О2. Работа при изменениях — 0–8

| Чем закрыт | Где смотреть |
|---|---|
| Все три типа сообщений кейса: файлом и руками из интерфейса | карточка «Сообщения в смену» |
| Расписание перестраивается с шага получения, прошлое не трогается | полотно, два слоя |
| Последствия для обязательств видны сразу | плитки итога до и после сообщения |
| Учёт невыполненных заданий сохраняется | фильтр «просроченные» на вкладке «Задания» |
| Что удалось сохранить — сказано числами | маршрут жюри «О2» |

**Статус: подтверждено.** Пример в репозитории: `examples/events_p01.json` отнимает
у JOB-0001 его единственный контакт и добавляет срочное задание — приоритетный счёт
не меняется, выручка растёт на $29,58, и обе половины этого видны в разборе.

### О3. Обоснованность решений — 0–8

| Чем закрыт | Где смотреть |
|---|---|
| Разбор задания в три слоя: данные, конкуренция, аппарат | панель «Разбор» на вкладках «Задания» и «Полотно» |
| Сертификат невыполнимости выдан против сценария, а не против нашего расписания | `planner/feasibility.py`, слой 1 разбора |
| Сертификат остаётся верным для просроченного задания | `feasibility.job_certificate(retrospective=True)` |
| Цена размена измерена повторным решением с форсированным заданием | слой 2 разбора, поле `counterfactual` |
| Причина отказа взята из журнала модели, а не придумана | слой 3 разбора, `reason` в `GET /trace` |
| Простой при открытом контакте показан отдельно | блок «чем были заняты аппараты» |
| Ограничения задачи отделены от недостатков алгоритма | основание цены слота: `unreachable_by_window` против `lost_to_selection` |

**Статус: подтверждено.** На P02 все 44 просроченных задания связи имеют
сертификат: ни одно из них не потеряно алгоритмом.

### О4. Сравнение управленческих вариантов — 0–7

| Чем закрыт | Где смотреть |
|---|---|
| Продолжения начинаются из одного состояния — это видно топологически | дерево на вкладке «Ветви», раскладка по шагу ветвления |
| Сопоставимость проверяется до чисел: сценарий, шаги, сообщения и их порядок | `core/compare.py`, блок вердикта |

## Чего нет и почему

| Что | Почему |
|---|---|
| 3D-глобус, орбиты, зоны видимости | геометрии в данных нет: у аппарата батарея, температура и ватты, у среды — `solar_w`, `thermal_target_c` и два булевых массива доступности. Орбиты пришлось бы выдумать, и они разошлись бы с окнами связи, по которым реально считается задача |
| Реальное время | постановка прямо говорит: пять минут модельного времени не требуют пяти минут ожидания. Ожидание сломало бы О5 |
| RL, CP-SAT | downlink решается точно потоком на этой размерности; относить задачу к обучению нечему |
| База данных, авторизация | смена живёт в памяти процесса; «данные запусков не смешиваются» решается ключом смены, а не хранилищем |
| Мобильная вёрстка | не оплачивается ни одним критерием |
